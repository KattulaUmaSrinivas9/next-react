Chat system architecture

A practical guide to how messages move through Next.js, RabbitMQ, and the Python worker, why the project uses this design, and how to configure it.

Next.js + Socket.IORabbitMQ request and response transportPython worker + PostgreSQL

01 · Overview

One broker carries both directions

Next.js publishes requests to a durable RabbitMQ queue. Python consumes each request, processes it, and publishes a response to a fanout exchange. Each active Next.js instance receives a copy in one temporary queue and emits only to its local matching Socket.IO room.

Delivery acknowledgment: the browser's accepted acknowledgment means RabbitMQ confirmed the request publish. Python completion is a separate step.

02 · Why this design

Trade-offs and responsibilities

Request queue

Buffers Python work

A durable queue retains requests while the worker is restarting. The worker acknowledges only after it has published the response.

Response fanout

Routes replies across instances

A fanout exchange sends each response copy to every active Next.js instance. Each instance emits only to its local matching room. Replies are not retained when there are no subscribers, like Redis Pub/Sub.

One broker

Fewer message services

RabbitMQ replaces both messaging services. It also adds broker availability, credentials, networking, and operations to manage.

At least once

Design for retries

A worker can receive a request again after a crash. Processing must be safe to repeat; message IDs support correlation.

Temporary retention: instance response queues are temporary and auto-delete after their consumer stops. Replies are live-only, not chat history. The app routes each response by both authenticated user and conversation.

03 · Message contracts

What crosses RabbitMQ

Request queue: chat.requests

{"userId":"authenticated-user","conversationId":"chat-uuid","messageId":"message-uuid","text":"SELECT 1;","createdAt":"ISO-8601"}

The user ID comes from the authenticated session. The conversation ID isolates separate chat windows.

Response exchange: chat.responses.fanout

{"userId":"authenticated-user","conversationId":"chat-uuid","messageId":"message-uuid","response":{"type":"text","content":"..."}}

Python publishes to the fanout exchange. Each active Next.js instance checks userId and conversationId against its local Socket.IO rooms.

04 · Runtime and configuration

Environment settings

Use the same broker URL and request/exchange names in Next.js and Python. For hosted brokers, use the TLS URL supplied by the provider, usually amqps://. Never commit credentials.

Local run

Run RabbitMQ, Next.js with npm run dev, and the Python worker with Uvicorn. Set RABBITMQ_URL=amqp://guest:guest@localhost:5672/%2F in both local env files. See the worker README for commands.

Vercel

Configure RABBITMQ_URL and matching queue/exchange names in the Next.js project and Python Daemon environment. The broker must allow outbound connections from both runtimes. Vercel Queues and Redis are not used by this flow.

05 · Follow a message

Logs and code map

Search Vercel logs by messageId and conversationId. Follow Next chat.socket.message_received → chat.queue.publish_succeeded → Python chat.queue.delivery_received / chat.queue.message_received → chat.processing.completed → chat.queue.response_published / chat.queue.request_acknowledged → Next chat.rabbitmq.response_received → chat.socket.response_emitted → chat.socket.response_delivery_confirmed → chat.rabbitmq.response_acknowledged. The delivery-confirmed event means the browser acknowledged handling the response. Browser console logs use the chat.client.* prefix.

Next.js

  • lib/chat-socket.ts — auth, conversation rooms, socket events.
  • lib/chat-queue.ts — durable request publisher.
  • lib/chat-realtime.ts — response queue consumer and emit.
  • vercel.json — Python daemon deployment.

Python

  • queue_worker.py — consume, process, publish response.
  • sql_execution.py — read-only SQL validation and execution.
  • pyproject.toml — runtime dependencies.

Python SQL accepts a single SELECT or WITH ... SELECT, runs read-only with a timeout, and caps results at 500 rows. Plain text still uses the demo response until a text-to-SQL provider is added.
