Chat system architecture

A developer's guide to how a browser message moves through Next.js, Vercel Queues, the Python worker, Neon PostgreSQL, Redis, and back to the connected user—and why each boundary exists.

Current implementation + roadmapUpdated 2 November 2026Monorepo / Vercel

01 · Start here

System at a glance

Durable background work and realtime browser delivery are separate concerns. A queue protects a user's request while Python works; Pub/Sub fans the result out to active Socket.IO servers.

Implemented

Direct SQL in chat

Paste one PostgreSQL SELECT or WITH … SELECT. Python validates it, executes with limits, and returns a table.

Planned

Plain-language questions

A model will translate natural language into candidate SQL. The same validation, executor, callback, and UI response path will remain.

Milestones are distinct: a chat acknowledgment means queued; a Python receive event means processing started; a table result means SQL succeeded; a browser event means the UI received it.

02 · Components

Runtime architecture

The top lane is durable request processing. The bottom lane is response delivery to connected users. The callback preserves authenticated user, conversation, and message IDs across the boundary.

03 · Lifecycle

One message end to end

Each mounted chat widget gets its own conversationId. Separate tabs therefore stay isolated; reloading creates a new conversation because chat history is not persisted yet.

  1. Connect. Browser opens Socket.IO at /api/socket-io. Next validates the chat session and joins the room scoped to authenticated userId + conversationId.
  2. Publish. Browser emits chat:message with conversationId. Next derives userId from the session, verifies the conversation matches the socket, sends to chat-messages, then returns chat:ack.
  3. Process. Python polls as consumer group chat-python-worker. A direct SQL message is validated and queried; other text currently uses the demo response.
  4. Return. Python POSTs {userId, conversationId, messageId, response} to /api/chat/results using the shared callback secret.
  5. Fan out. Next validates the callback. It publishes to Redis, whose Socket.IO subscribers emit only to the room scoped by userId and conversationId. Without Redis locally, the callback emits directly through the local server.
  6. Render. The browser receives chat:response and renders the response union: text, table, chart, image, or video.

04 · Design rationale

Why the system uses these approaches

Inbound request

Queue instead of running SQL in Socket.IO

DB/model work can be slow or fail transiently. A queue keeps the socket handler short, buffers work while Python is busy, and retries when processing fails.

Trade-off: the UI receives an asynchronous result later, correlated by messageId.

Live response

Pub/Sub instead of a response queue today

Every active Socket.IO process can subscribe and emit to a local room scoped by authenticated user and conversation. This is the current cross-instance realtime fan-out.

Trade-off: Pub/Sub is ephemeral; offline subscribers do not replay messages.

Ownership

Python owns SQL and DB credentials

Database access and query policy stay server-side in one worker. The browser and client bundle never receive a Neon credential.

Trade-off: Python needs its own runtime, logs, health checks, and env configuration.

Trust boundary

Authenticated callback

The worker calls a Next route using a shared bearer secret. Next validates both the secret and response shape before realtime delivery.

Trade-off: URL and secret must be correct and reachable in both environments.

Why not two queues?

A chat-responses queue is possible, but Next still needs a consumer to read it and deliver to the Socket.IO instance holding the user's connection. That still needs realtime routing. If users must recover missed responses, persist them and fetch on reconnect. A second queue is useful for durable response processing or independent consumers; it does not itself push to a browser.

Different delivery guarantees: Vercel Queues are at-least-once, so handlers must tolerate retries. Redis Pub/Sub is at-most-once, so it is suitable for live fan-out, not durable history.

05 · Interfaces

Message contracts

Queued request

{
  "conversationId": "client-generated-chat-id",
  "messageId": "stable-client-generated-id",
  "userId": "authenticated-user-id",
  "text": "SELECT 1 AS db_check;",
  "createdAt": "ISO-8601 timestamp"
}

messageId is the queue idempotency key. userId is derived from the authenticated session, not trusted from client input.

Python result callback

{
  "userId": "authenticated-user-id",
  "conversationId": "client-generated-chat-id",
  "messageId": "stable-client-generated-id",
  "response": {
    "type": "table",
    "title": "Query results",
    "columns": ["db_check"],
    "rows": [{"db_check": 1}]
  }
}

The response uses the assistant response type union. The Next callback rejects unauthorized or malformed results before publishing them.

06 · Data access

Current SQL execution

Recognize

Direct text beginning with SELECT or WITH is SQL. A Markdown SQL fence is supported.

Parse

sqlglot parses PostgreSQL syntax and only one query statement is accepted.

Execute

psycopg runs in a PostgreSQL read-only transaction with a 10-second statement timeout.

Return

At most 500 rows become a table. Decimal, date, UUID, JSON, and binary values are converted for UI display.

Schema names matter

PostgreSQL searches only schemas on search_path. If the ER diagram's group labels are actual schema names, qualify relations such as catalog.products, catalog.categories, sales.order_items, and app.customers. An unqualified products can fail with PostgreSQL 42P01 even when catalog.products exists.

Credential boundary: set the real Neon URL as DATABASE_URL in the Python worker environment only. Use a database role granted only required SELECT permissions.

07 · Future design

Text-to-SQL without changing the execution boundary

  1. Choose a model provider and put its credential in the Python environment, not source control or the browser.
  2. Send only relevant tables, columns, relationships, and business definitions as context; do not expose sensitive columns by default.
  3. Request structured candidate SQL. Do not give the model direct database credentials or execution tools.
  4. Parse and validate generated SQL again. Require one allowed SELECT; reject writes, DDL, multiple statements, and disallowed functions.
  5. Reuse the current read-only role, timeout, result cap, response shaping, callback, and Socket.IO flow.
  6. Consider showing generated SQL to the user for transparency; avoid logging sensitive prompts or query literals.

Provider remains undecided. The text-to-SQL layer should call a provider adapter so the executor is independent of the model vendor.

08 · Run and deploy

Operational model

Local

Run the Queue devserver on port 8111, Next/Socket.IO on 3000, Python FastAPI plus poller on 8000, then open the browser. The Python lifespan starts polling. /health confirms only that FastAPI is alive.

Use the complete commands in Python worker local development.

The custom server.ts loads Next env files before dynamically importing chat handlers because the queue client reads environment variables during module initialization.

Vercel Production

Deploy this monorepo as one Vercel project. The Python worker is declared as a daemon in vercel.json in region iad1. Producer and worker must use the same project/queue scope.

Set the callback secret consistently, point NEXT_API_BASE_URL to the deployed app, configure REDIS_URL, and set the real Neon URL for the Python runtime.

Leave local queue URL/token unset on Vercel. Let the Vercel runtime provide queue credentials; never store copied short-lived tokens.

09 · Reliability and security

Boundaries to preserve

  • Identity and conversation isolation: derive userId from the authenticated session; scope socket rooms by userId plus conversationId, and verify each event matches the connected socket.
  • Callback: authenticate the worker and validate the response shape before publish.
  • Database: keep the Neon URL in Python config and use a role with only required read grants.
  • SQL: preserve parse checks, read-only transaction, timeout, and row cap. Database grants remain the final permission boundary.
  • Logs: correlate by messageId. Never log URLs, credentials, raw chat messages, or sensitive result data.
  • Retries: queue messages can be delivered again. Any future side effect or model operation must tolerate duplicate processing.
  • Realtime: Pub/Sub does not guarantee a browser received an event. Add response persistence and reconnect fetch if that becomes a requirement.
Demo authentication: current login is demo-grade. Before real customer data, replace it with production identity and enforce per-user data authorization.
